# Self-Improvement Loop

Backbone Protocol is not just a way to run one project well.

It is also a way to turn solved problems into reusable infrastructure for future projects.

## Core Principle

> A solved problem should not disappear into chat history. It should become reusable infrastructure.

## Loop

```text
execute workflow
  -> capture workflow trace
  -> evaluate output
  -> distill lesson
  -> promote reusable pattern
  -> update skill/template/checklist/eval
  -> rerun examples/evals
```

## 1. Execute Workflow

Run the project using the normal backbone phases.

The point is not to invent a separate improvement workflow before any real work exists. Improvement starts from actual execution.

## 2. Capture Workflow Trace

Record what happened in `workflow_trace.md`:

- what the goal was
- what context was used
- which steps were effective
- where confusion appeared
- what decisions mattered
- what reusable pattern might exist

## 3. Evaluate Output

Ask what went well and what did not.

Possible questions:

- Which steps were fragile?
- Which instructions were repeatedly needed?
- Which failures were avoidable?
- Which artifact was missing or too weak?

## 4. Distill Lesson

Turn the trace into a reusable lesson:

- failure mode
- missing checklist item
- prompt refinement
- better template structure
- skill clarification

The lesson should be specific enough to reuse, not just narrative.

## 5. Promote Reusable Pattern

If the lesson generalizes, promote it into one of the repository's reusable layers:

- skill
- template
- checklist
- evaluation rule
- docs clarification

This is how the repo compounds over time.

## 6. Update Shared Infrastructure

Make the smallest reversible update that captures the lesson.

Examples:

- add a stop condition to a skill
- strengthen a model-card template
- clarify a data-audit checklist
- add a worked example

## 7. Rerun Examples Or Evals

Once the improvement is promoted, verify that it helps.

That may mean:

- rerunning a docs build
- checking a worked example
- validating the updated workflow against a prior failure mode

## Why This Matters

Without this loop:

- projects improve, but the system does not
- good judgment stays trapped in individual sessions
- teams repeat the same mistakes

With this loop:

- repeated work becomes reusable structure
- handoffs become easier
- future agent sessions start from a stronger baseline
